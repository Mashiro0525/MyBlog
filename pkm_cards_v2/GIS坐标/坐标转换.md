## 35. 修改地理坐标系查询、修改轴序后依然返回空值

**问题：** 修改地理坐标系查询、修改轴序后依然返回空值

**答案：** 如果修改了地理坐标系声明（EPSG:4326）并尝试了轴序交换后依然返回空值，说明问题不在于简单的语法，而在于虚幻引擎生成的经纬度与 GeoServer 数据的实际物理位置不重合。

为了消除 (Elimination) 这种“看不见”的物理偏移，请按照以下步骤进行排查和修正：

1. 核心定位：GeoServer 内部坐标验证

这是最有效的消除 (Elimination) 方案。我们要确认 GeoServer 认为该点应该是什么坐标。

进入 GeoServer 后台，点击 Layer Preview (图层预览)。

找到你的 UE_JiJiHu:landuse 图层，点击 OpenLayers。

在打开的地图页面中，点击一个你确定有属性的地块。

关键动作：观察浏览器下方显示的点击坐标，或者查看浏览器开发者工具（F12）的网络请求（Network），找到它自动生成的 GetFeatureInfo 或 GetFeature URL。

对比该 URL 中的 POINT(...) 数值与你在虚幻引擎蓝图中生成的数值。

2. 投影坐标系 (EPSG:4539) 的特殊性

由于你的原始数据是 EPSG:4539（高斯-克吕格 3 度带，中央经线 87°E），这类投影坐标系对坐标顺序和范围极其敏感。

消除 (Elimination) 顺序干扰：尝试在浏览器手动输入投影坐标（单位为米）进行测试。例如：
...&cql_filter=INTERSECTS(the_geom,POINT(X坐标 Y坐标))&srsName=EPSG:4539
(X/Y 数值从 Layer Preview 的 OpenLayers 中获取)。

如果米制坐标能搜到，经纬度搜不到：说明 GeoServer 在处理该特定投影转换时存在障碍，你需要在虚幻引擎蓝图中使用 Georeferencing 插件 将经纬度先转换为 EPSG:4539 的米制坐标。

3. 检查虚幻引擎中的 Georeference 设置

如果 GeoServer 数据没错，但虚幻传出的点不对，请检查：

Origin Location：在 CesiumGeoreference 或引擎自带的 Georeferencing 类中，确认你的 Origin Latitude/Longitude 是否与实际地块位置匹配。

坐标偏离：如果你的 UE 场景模型是手动拖放的，可能导致点击获取的经纬度与地块实际地理位置有几百米的偏差，从而消除 (Elimination) 了命中的可能。

4. 终极兼容性设置：使用 WFS 1.1.0

WFS 1.0.0 对轴序的处理在不同版本 GeoServer 中存在差异。尝试升级协议版本来消除 (Elimination) 规范歧义：

将 URL 中的 version=1.0.0 改为 version=1.1.0。

在 WFS 1.1.0 中，EPSG:4326 的标准顺序严格要求为 (纬度 经度)。

5. 调试策略建议

范围查询测试：为了验证数据是否真的在那里，将 INTERSECTS 的 POINT 改为一个巨大的 BBOX（边界盒）。
&bbox=经度1,纬度1,经度2,纬度2,EPSG:4326
如果 BBOX 能返回数据而 POINT 搜不到，说明你的点击点确实落在了地块空隙中。

图层名校验：再次确认 typeName 后面的图层名大小写完全正确，确保没有因为图层名指向错误而消除 (Elimination) 了所有查询结果。

通过对比 Layer Preview 产生的“绝对正确”的坐标，你就能发现虚幻引擎传出的坐标到底偏移了多少，进而通过调整引擎的地理参照设置来消除 (Elimination) 这个空间偏差。

## 36. 在虚幻引擎蓝图中怎么使用 Georeferencing 插件将经纬度转换为 EPSG:4539 的米制坐标

**问题：** 在虚幻引擎蓝图中怎么使用 Georeferencing 插件将经纬度转换为 EPSG:4539 的米制坐标

**答案：** 在虚幻引擎中，利用 Georeferencing 插件将地理经纬度转换为特定的投影坐标系（如 EPSG:4539）的米制数值，可以有效消除 (Elimination) 因单位不统一导致的 GIS 查询失败。

以下是实现这一转换的详细步骤：

1. 插件与环境准备

启用插件：在编辑器中点击 Edit > Plugins，搜索并启用 Georeferencing 插件，随后重启编辑器。

添加系统 Actor：从“放置 Actor (Place Actors)”面板中，搜索 Geo Referencing System 并将其拖入你的关卡。

配置坐标系：

选中该 Actor，在“细节 (Details)”面板中，将 Projected CRS 设置为自定义。

在 Projected CRS String 栏中输入：EPSG:4539。

确保 Geographic CRS 设置为 EPSG:4326（标准经纬度）。

2. 蓝图逻辑实现 (Graph Recipe)

在你的 PlayerController 或处理点击逻辑的蓝图中，按照以下顺序连接节点：

获取引用：使用 Get GeoReferencingSystem 节点（通过 Get Actor of Class 获得场景中该 Actor 的引用）。

构建地理坐标结构体：

添加 Make GeographicCoordinates 节点。

将你点击获取的经度 (Longitude) 连入 Longitude，纬度 (Latitude) 连入 Latitude。

执行坐标转换：

从 GeoReferencingSystem 引用拉出线条，调用 Geographic to Projected 节点。

将上一步创建的结构体连入该节点的输入。

提取投影数值 (米)：

使用 Break CartesianCoordinates 节点分解转换后的结果。

输出的 X 和 Y 即为符合 EPSG:4539 标准的米制坐标。

3. 将转换结果接入 HTTP URL

为了将这些米制坐标发送给 GeoServer，你需要更新拼接字符串的逻辑：

使用 Format Text 或 Append 节点。

格式示例：
...&cql_filter=INTERSECTS(the_geom,POINT({X} {Y}))&srsName=EPSG:4539
(注意：此时 URL 结尾的 srsName 必须对应设置为 EPSG:4539)。

4. 关键注意事项与性能优化

双精度支持：Georeferencing 插件在内部使用双精度浮点数（Double）进行计算，这能极大消除 (Elimination) 大场景下的坐标精度损失，确保你的点击点与地块边界完美重合。

轴序核对：EPSG:4539 是高斯-克吕格投影，在 WFS 请求中通常使用 X (Easting) 和 Y (Northing)。如果请求依然返回空，请尝试在 POINT 中交换 X 和 Y 的位置。

消除 (Elimination) 偏移偏差：请确保 Geo Referencing System Actor 中的 Origin Location（原点位置）与你场景在 Cesium 或其他底图插件中的原点设置完全一致。

5. 验证方法

你可以使用 Print String 打印出转换后的 X 和 Y。如果数值在 500000 或 4900000 左右的量级，说明转换成功，这正是 EPSG:4539 投影坐标系应有的单位特征。这将彻底消除 (Elimination) 之前使用 88.8、44.7 等“度”单位查询“米”制图层时产生的逻辑错误。

## 37. 将http GET请求前的射线检测加入使用 Georeferencing 插件将经纬度转换为 EPSG:4539 的米制…

通过这套整合逻辑，你点击地图的不同地块时，发送给 GeoServer 的 POINT(X Y) 将会是基于投影坐标系的动态米制坐标，从而实现精准的要素查询。

## 48. 通过鼠标点击CesiumWebMapServiceRasterOverlay图层，将cesium坐标转为4539投影坐标…

**问题：** 通过鼠标点击CesiumWebMapServiceRasterOverlay图层，将cesium坐标转为4539投影坐标系，再调用geoserver数据库获取属性值，再利用json文本解析返回的数值传送到UI设置的文本中，整个过程实现后鼠标点击无返回值，该如何排查全流程可能的卡点。

**答案：** 实现“点击地图 -> 坐标转换 -> 请求 GeoServer -> 解析 JSON -> 更新 UI”的流程非常复杂，任何一环出错都会导致最终结果为“空”。

要排查这种“静默失败（Silent Failure）”，必须在每一个关键节点添加“断点式”日志（Print String 或 UE_LOG）。以下是按流程拆解的 5 个核心排查点及解决方案：

1. 坐标拾取阶段：Cesium 拾取是否有效？

可能卡点：点击到了天空、未加载的瓦片，或者 Cesium 的 Line Trace 未命中。

排查方法：在获取到 Cartographic（经纬度）坐标后，立即打印。

检查逻辑：

经纬度是否为 (0,0,0)？如果是，说明射线检测没打中地图。

确保使用了 Cesium Sample Height Most Detailed 或类似的节点，并在 On Success 分支后执行后续逻辑，以消除 (Elimination) 高度数据未加载导致的空值。

2. 坐标转换阶段：EPSG:4539 转换是否正确？

可能卡点：GeoReferencing 插件配置错误。EPSG:4539 是一个特定的投影坐标系，插件必须知道这个定义。

排查方法：打印转换后的 X 和 Y 值。

核心配置：

在关卡中的 GeoReferencingSystem 演员里，确认 Projected CRS 是否填入了正确的定义（如 EPSG:4539）。

如果是自定义投影，可能需要完整的 PROJ4 字符串。

注意：如果返回的 X, Y 是极大或极小值，说明转换逻辑失败，需消除 (Elimination) 投影参数配置不当的问题。

3. 请求构建阶段：GeoServer URL 是否合法？

可能卡点：拼接的 URL 字符串存在特殊字符未转义，或者参数名错误。

排查方法：在调用 HTTP Request 之前，使用 Print String 打印完整的 URL。

手动验证：将打印出的完整 URL 复制到浏览器中直接访问。

如果浏览器返回错误或空 JSON，说明你的 BBOX、X/Y 或 QUERY_LAYERS 参数拼接逻辑有误。

确保 INFO_FORMAT 设为 application/json 以便后续解析。

4. 网络通信阶段：请求是否到达并返回？

可能卡点：网络请求超时、GeoServer 跨域拦截，或返回了非 200 的状态码。

排查方法：

在回调中检查 Response Code。只有 200 才是成功。

打印 Content（原始响应字符串）。如果 Content 为空，说明服务器没有返回任何特征数据。

异步陷阱：确保所有后续逻辑都在 On Process Request Complete 事件之内执行，否则会因为“数据还没回来就去解析”而导致空值，从而消除 (Elimination) 异步竞争问题。

5. 解析与 UI 阶段：JSON 路径是否匹配？

可能卡点：GeoServer 返回的 JSON 嵌套层级深，字段名大小写不匹配。

排查方法：

将原始响应字符串放入在线 JSON 解析器查看结构。

在蓝图中，使用 Get Field 节点时，确认字段名（如 features -> properties -> your_field）完全匹配。

UI 线程：确保最后 Set Text 的目标 UI 引用是有效的（非 Null）。

推荐的排查路径图：

[鼠标点击]

 -> [Print: Lat/Long] <--- 检查是否点击成功

 -> [HTTP 调用]
 |-> [On Complete]

通过这种分段打印的方法，你可以定位到具体是哪一个环节将数据“丢失”了。通常情况下，坐标转换误差或 GeoServer 参数不匹配（如坐标轴翻转 X/Y 颠倒）是导致消除 (Elimination) 返回值的主要原因。

## 49. 打印Hit Result Impact Point，当点击的地形距离很近时，坐标数值被正常打印；当位于鸟瞰视角时，点击c…

**问题：** 打印Hit Result Impact Point，当点击的地形距离很近时，坐标数值被正常打印；当位于鸟瞰视角时，点击cesium地形屏幕无坐标被打印

**答案：** 这说明你的射线检测（Line Trace）存在最大距离限制，或者远距离地形的碰撞体未加载。在鸟瞰视角（高空）点击时，射线在触达到地面之前就已经达到了它的预设终点，从而导致检测失败。

请按照以下步骤排查并消除 (Elimination) 远距离点击失效的问题：

1. 修改“按通道获取光标下的命中结果”的距离限制

该内置节点在某些引擎版本或配置下，其默认射线长度（Trace Distance）可能不足以覆盖极高空的鸟瞰视角。

解决方法：弃用该简易节点，改用手动射线检测。

蓝图方案 (Graph Recipe)：

从 Player Controller 节点拉出 Get Mouse Service 或使用 Convert Mouse Location to World Space。

得到 World Location（起点）和 World Direction（方向）。

计算 End Point：World Location + (World Direction * 1000000.0) (将乘数设为一个极大值，如 10 公里)。

使用 Line Trace By Channel 节点，连接 Start 和 End。

效果：通过极大化 End 值，消除 (Elimination) 因距离过远导致的射线中断。

2. 检查 Cesium 地形的碰撞加载设置

Cesium for Unreal 使用瓦片（Tileset）系统。当你在极高空鸟瞰时，远处的地面可能只加载了低精度（LOD）模型，而这些低精度模型默认可能没有生成碰撞体。

操作：

在场景中选中 CesiumGeoreference 关联的 Cesium3DTileset 资产。

在 Details 面板搜索 Collision。

勾选 Create Physics Meshes（确保开启）。

找到 Always Load On Client 或相关的 Collision Mips 设置。

注意：如果设置了“仅在最高精度加载碰撞”，那么鸟瞰时的低精度瓦片将无法被射线击中。

3. 验证“命中失败”的原因

为了确认是“没打到”还是“打不到”，请在逻辑中加入调试：

操作：在 Line Trace By Channel 节点的 Draw Debug Type 选项中选择 For Duration。

观察：

如果看到一条红线射向地面但在半空停止，说明是 距离太短。

如果红线穿过了地面或消失在天际，说明是 地面没有碰撞体。

4. 消除 (Elimination) 坐标精度导致的打印消失

当坐标数值极大（如 Cesium 常用世界坐标）时，某些自动转换逻辑可能出错。

操作：使用 Break Hit Result 节点，从 Blocking Hit 引脚连出一个 Branch。

False 分支：接 Print String ("Out of Range or No Collision")。

结论：如果你在鸟瞰时点击屏幕打印了 “Out of Range”，则证实了射线长度或碰撞体缺失的问题。

5. 调整相机远裁剪面 (Far Clip Plane)

虽然这通常影响视觉显示，但如果相机远裁剪面设置过短，有时也会干扰相关的转换逻辑。

检查 Project Settings -> General Settings -> Near Clip Plane。

在你的相机组件中检查 Far Clip Plane 是否足够大。

建议总结：
最有效的解决办法是手动构造长距离射线（步骤 1），并将射线长度设为 1,000,000 以上。这样可以完全消除 (Elimination) 鸟瞰视角下因高度过大导致的射线检测“够不着”地面（Impact Point 为空）的问题。

## 50. 发送 HTTP Request 前打印完整的 URL，复制此 URL 到浏览器手动访问，因为点的坐标错误导致返回空值。g…

**问题：** 发送 HTTP Request 前打印完整的 URL，复制此 URL 到浏览器手动访问，因为点的坐标错误导致返回空值。geoserver中图层的X值范围是408230-414874，但GeoReferencingSystem 转换后的 Projected X数值范围在500000以上，同理Y值的数值范围是4958698-4965025，GeoReferencingSystem 转换后的 Projected X数值范围在5000000以上。应该如何解决

**答案：** 这说明你的 GeoReferencingSystem 中配置的 Projected CRS (坐标参考系) 与 GeoServer 图层使用的实际坐标系存在偏差。虽然数值量级接近，但由于“中央子午线”或“投影带”的定义不同，产生了约 100km (X轴) 和 几十km (Y轴) 的偏移。

要消除 (Elimination) 这种坐标不匹配，请按以下步骤调整：

1. 确认 GeoServer 的精确 EPSG 代码

首先，你必须查明 GeoServer 图层到底使用的是哪个坐标系。

操作：登录 GeoServer 后台 -> 点击左侧 Layers（图层） -> 找到你的图层。

检查：查看 Coordinate Reference Systems 部分的 Native CRS 或 Declared CRS。

重点：如果 GeoServer 显示的是 EPSG:4544、EPSG:4545 等，而你填的是 EPSG:4539，即使它们都是 CGCS2000 投影，其分带（Zone）或中央经线也不同，会导致数万米的误差。

2. 检查 GeoReferencingSystem 的 CRS 字符串

一旦确认了 GeoServer 的 EPSG 代码（例如是 4545），请在虚幻引擎中更新：

操作：选中场景中的 GeoReferencingSystem Actor。

修改：在 Projected CRS 栏中输入 EPSG:4545 (确保格式严格一致)。

验证：点击编译并重新运行，观察 Projected X/Y 是否回落到了 408xxx 和 495xxxx 范围内。

3. 处理“轴顺序 (Axis Order)”引起的偏移

这是 GIS 转换中最常见的陷阱：

某些坐标系定义 X 为经度，Y 为纬度；另一些则相反。

如果你的 X 变成了 500w+，而 Y 变成了 40w+，说明 经纬度顺序反了。

消除 (Elimination) 方案：在 GeoReferencingSystem 的 CRS 字符串后添加轴顺序参数（如果使用的是 PROJ 字符串），或者在蓝图中交换转换后的 X 和 Y 值后再进行 URL 拼接。

4. 消除 (Elimination) False Easting（东偏移）影响

你提到的 500000 这个数值非常敏感，因为在 UTM 或高斯-克吕格投影中，为了避免出现负数，通常会将中央子午线定义为 500,000 米。

如果你的 GeoServer 数据是去除了 500km 偏移的相对坐标，而 UE5 输出的是绝对投影坐标，你需要在蓝图中手动减去这个偏移。

操作：Final_X = Projected_X - 500000.0。

5. 在浏览器中反向验证

为了快速定位问题，你可以从 GeoServer 的图层预览中随便找一个点的坐标（例如 X: 410000, Y: 4960000），然后在你的蓝图逻辑中加入一个测试节点：

测试节点：使用 Projected to Engine 节点，输入这个正确的坐标。

观察：看它生成的 3D 点位是否落在了 Cesium 地形的对应位置。

如果位置正确：说明 UE5 的系统配置是对的，只是你点击抓取的点不对。

如果位置偏离了上百公里：说明 GeoReferencingSystem 里的 EPSG 代码选错了。

总结建议

既然坐标差了约 10 万米，这通常意味着投影带（Zone）选错了一个带位（每个带通常宽 3 度或 6 度）。请务必回到 GeoServer 确认其图层属性中的 EPSG 代码，并将其完整、准确地复制到虚幻引擎的系统设置中，从而消除 (Elimination) 这种系统性的投影偏差。

## 51. GeoReferencingSystem的Origin Projected Coordinates Easting和Or…

**问题：** GeoReferencingSystem的Origin Projected Coordinates Easting和Origin Projected Coordinates Northing不为零，坐标偏移是否和这个设置有关

**答案：** 是的，这正是导致坐标偏移的直接原因。

在 Unreal Engine 的 GeoReferencingSystem 中，Origin Projected Coordinates 的作用是定义 Unreal 世界原点 (0,0,0) 在投影坐标系（CRS）中对应的位置。

1. 偏移原理分析

当你在蓝图中调用 Engine to Projected 函数时，引擎执行的逻辑实际上是：
[绝对投影坐标] = [Unreal 局部坐标] + [Origin Projected Coordinates]

如果你的 GeoServer 数据使用的是绝对投影坐标（即以该坐标系的 0 点为基准），而你的 Origin Projected Coordinates 设置了 500,000，那么即便你在 Unreal 原点点击，转换出的结果也会被强行加上这 500,000。

这解释了为什么你的 X 坐标变成了 500,000+，而 GeoServer 图层范围只有 408,230-414,874。

2. 解决方案：如何消除 (Elimination) 偏移

根据你的项目需求，有两种修复方案：

方案 A：归零原点（推荐用于绝对坐标匹配）

如果你的 GeoServer 数据和 Cesium 地形都是基于标准 EPSG 代码的绝对位置：

选中场景中的 GeoReferencingSystem。

将 Origin Projected Coordinates Easting 设为 0.0。

将 Origin Projected Coordinates Northing 设为 0.0。

结果：此时 Engine to Projected 输出的将是纯粹的绝对 CRS 坐标，应该会直接落在 408xxx 范围内。

方案 B：精确对齐原点

如果你的 Unreal 原点 (0,0,0) 必须位于某个特定的地理位置：

你必须确保 Origin Projected Coordinates 填入的值，恰好是 Unreal 原点在 GeoServer 坐标系下的精确投影值。

如果不确定该值，最简单的方法是使用方案 A。

3. 处理“无访问 (Accessed None)”报错的连锁反应

当你将原点归零或修正后：

Engine to Projected 转换出的坐标将重新回到 408xxx 范围内。

发送给 GeoServer 的 URL 将能正确命中图层特征。

GeoServer 返回的 features 数组将不再为空（Length > 0）。

消除 (Elimination) 结果：原本因为数组为空导致的 CallFunc_Array_Get_Item 报错将随之消失。

4. 验证步骤

修改 Origin Projected Coordinates 为 0。

运行程序，在 Cesium 地形上点击。

观察 Print String 打印出的 Projected X。

确认：该数值是否现在处于 408230 - 414874 之间。

5. 性能与最佳实践提醒

消除 (Elimination) 精度浮动：由于 Cesium 处理的是全球尺度，请确保在蓝图中处理这些大数值时使用 Double（双精度） 引脚。

防御性检查：即便修正了原点，仍然建议在蓝图中保留 Array Length > 0 的判断分支，以防止用户点击到图层范围之外的区域时程序崩溃。

通过将 Origin Projected Coordinates 归零，你就可以消除 (Elimination) 系统自动添加的位移量，使 Unreal 的坐标输出与 GeoServer 的数据规范达成完全一致。

## 52. 将Origin Projected Coordinates Easting 设为 0.0、将 Origin Projec…

**问题：** 将Origin Projected Coordinates Easting 设为 0.0、将 Origin Projected Coordinates Northing 设为 0.0后，返回的geographic to projectedX/Y又变为了极小值，是否应该重新设置这两个数值

**答案：** 如果你将 Origin Projected Coordinates 设为 0.0 后，转换出的值变成了极小值（接近 0），这说明你的 Unreal 世界原点 (0,0,0) 并没有位于你所期望的地理区域（即 Cesium 瓦片所在的区域），或者你的 GeoReferencingSystem 并没有正确获取到 Cesium 瓦片的地理参照。

你应该重新设置这两个数值，但不能盲目设置，而是要通过校准（Calibration）来找到正确的对齐值。

以下是修复并消除 (Elimination) 坐标偏差的步骤：

1. 理解校准逻辑

当你使用 Cesium 时，Cesium 会将地球上某个经纬度点（例如你的项目所在地）放置在 Unreal 的 0,0,0 位置。
为了让 Engine to Projected 正常工作，你需要告诉 GeoReferencingSystem：Unreal 的 0,0,0 点对应的投影坐标是多少？

2. 如何获取正确的 Origin 数值

请按照以下步骤手动校准：

找到参考点：在场景中，找一个你确信在 GeoServer 图层范围内的位置（例如图层中心）。

获取 Unreal 坐标：将你的玩家角色或一个静态网格体（Static Mesh）移动到该点，记录下它的 Relative Location（例如 X=100, Y=200）。

获取该点的投影坐标：

查看你的 GeoServer 数据。假设该点在 GeoServer 里的坐标应该是 X=410000, Y=4960000。

计算并填入 Origin：

Easting = 410000 - (Unreal_X / 100) (注意：Unreal 单位是厘米，需转换为米)。

Northing = 4960000 - (Unreal_Y / 100)。

将计算出的这两个值填入 GeoReferencingSystem 的 Origin Projected Coordinates 中。

3. 更简单的“自动校准”方法

如果你使用了 CesiumGeoreference 资产，通常它会驱动地理参考。

操作：在 GeoReferencingSystem 的细节面板中，查看是否有 “Origin Latitude/Longitude”。

对齐：确保这里的经纬度与你 CesiumGeoreference 资产中设置的 Origin Latitude/Longitude 完全一致。

消除 (Elimination) 差异：一旦经纬度原点对齐，点击 “Apply” 或重新生成，系统会自动计算出对应的 Projected Easting/Northing。

4. 再次检查轴顺序 (Axis Mapping)

如果你填入了正确的值，但 X 和 Y 的范围依然错乱：

在 GeoReferencingSystem 设置中，检查 Environment Settings。

确保 Internal CRS 映射正确。通常 UE 默认是 X=East, Y=North, Z=Up。如果你的 GeoServer 期望 X=North，你需要在这里交换映射关系，以消除 (Elimination) 轴向混乱。

5. 验证 Accessed None 报错

在填入新的 Origin 值后，立即观察你的 HTTP 请求：

打印 URL：查看 URL 中的 X 是否回到了 408xxx。

数组长度：如果 URL 里的坐标落入范围，Array Length 应该从 0 变为 1。

结果：这将直接消除 (Elimination) 之前因为数组为空导致的 CallFunc_Array_Get_Item 报错。

总结建议

不要将 Origin 设为 0.0，因为这意味着 Unreal 的原点在地球的投影中心点。你应该将其设置为你的项目中心点在 EPSG:4539 下的绝对坐标值（大约是 Easting: 410000 左右）。这样，你在 Unreal 中点击时，输出的 Projected 坐标才能正确落入 GeoServer 的图层范围内。

## 55. 如何获取CesiumGeoreference的Origin Latitude是44.775409、Origin Long…

**问题：** 如何获取CesiumGeoreference的Origin Latitude是44.775409、Origin Longitude是88.834102、Origin Height是429.114545对应ue、

**答案：** 当你在 GeoReferencingSystem 中取消勾选 Origin Location in Projected CRS 并直接输入经纬度时，引擎会自动计算对应的投影坐标。出现 1000-2000米 的误差，通常是因为 UE5 默认的地理转换（基于 PROJ 库）与 GeoServer 内部使用的 Datum（大地基准面）转换参数 或 中央子午线（Central Meridian） 定义不完全一致。

要消除 (Elimination) 这最后的 1~2 公里误差，请按照以下步骤进行“增量校准”：

1. 采用“手动补偿”法（最有效）

既然误差已经缩小到了 2000 米以内，说明投影带是正确的，只是基准面位移。

重新勾选 Origin Location in Projected CRS。

你会看到 Easting 和 Northing 自动生成了数值（基于你之前填的经纬度）。

计算偏移：

在场景中点击一个你已知确切位置的点（例如某个建筑物）。

看打印出的 Projected X 比 GeoServer 里的 X 大了还是小了。

如果 UE5 打印的是 412,000，而 GeoServer 应该是 410,500，说明 UE5 偏大了 1,500 米。

修正数值：

将 Origin Projected Coordinates Easting 减去这个 1,500。

对 Northing 进行同样的减法（或加法）操作。

消除 (Elimination) 结果：通过这种手动微调，你可以强制将 Unreal 的坐标系与 GeoServer 的图层完全重合。

2. 检查 EPSG 兼容性

GeoServer 上的 EPSG:4539 对应的是 CGCS2000 / Gauss-Kruger CM 87E。

确认 GeoServer 里的数据是否有“七参数”或“三参数”转换？

如果 GeoServer 数据经过了特殊的坐标转换，而 UE5 只是进行标准的数学投影，就会产生这种公里级的位移。

消除 (Elimination) 策略：不要强求经纬度输入后的自动转换，直接以 Projected Coordinates 数值模式进行手动平移（如步骤 1 所示）。

3. 防止蓝图崩溃（针对报错的永久方案）

即便存在 1000 米的误差，也不应该导致蓝图崩溃。请务必检查 A_PlayerController：

蓝图节点检查 (Must Do)：

在执行 Array Get (Index 0) 之前，插入一个 Length 节点。

接一个 Branch (条件：Length > 0)。

只有在数组不为空时，才去访问元素。

消除 (Elimination) 报错：这样即使坐标还有 1000 米误差导致请求不到数据，控制台也只会打印“未找到要素”，而不会抛出红色运行时错误。

4. 为什么会有 1~2 公里的误差？

这种量级的误差通常来自：

中央子午线的微小差异（87度还是附近的度数）。

椭球体差异（WGS84 还是 CGCS2000）。UE5 默认可能在用 WGS84 的参数计算投影，而 CGCS2000 在某些地区与 WGS84 有微小位移。

坐标系投影原点（False Northing）：由于你使用的是高斯-克吕格投影，投影原点的计算非常敏感。

总结操作序列

记录当前经纬度生成的 Easting/Northing 数值。

切换回 Origin Location in Projected CRS（勾选）。

手动加减 Easting/Northing 数值（约 1000-2000 的修正量），直到点击位置打印出的 X/Y 与 GeoServer 预览中的坐标完全对齐。

保存项目，确保变量引用通过 Get Actor of Class 动态获取，从而消除 (Elimination) 重新打开项目后的引用失效。

## 11. 不更改game mode和HUD能否加载AirSim的操作页面

**问题：** 不更改game mode和HUD能否加载AirSim的操作页面

**答案：** 在虚幻引擎中，不更改全局 GameMode 和 HUD 设置而加载 AirSim 的操作页面（HUD）是完全可行的。AirSim 的界面本质上是一组 UMG Widget，你可以通过手动实例化的方式将其“挂载”到你现有的 UI 框架中。

以下是实现这一目标的具体技术路径和蓝图逻辑，旨在帮助你消除 (Elimination) 对固定 GameMode 的依赖。

1. 核心原理

AirSim 的运行并不强制锁定在 AirSimGameMode 下，其核心逻辑由场景中的 SimMode（模拟模式）Actor 驱动。

GameMode 的默认作用仅仅是自动生成一个 SimMode Actor 并配置默认的 HUD。

解决方案：只要你在场景中手动放置一个 SimMode Actor，并手动创建 AirSimHUD 的 Widget 即可。

2. 操作步骤

A. 环境准备

在内容浏览器中搜索 BP_SimModeWorldMultiRotor（如果你使用无人机）。

将该 Actor 手动拖入 你的关卡场景中。

确保你的 settings.json 文件已配置正确，否则 SimMode 会因为无法初始化而消除 (Elimination) 模拟进程。

B. 手动加载 AirSim UI (蓝图实现)

在你现有的 PlayerController 或 Level Blueprint 的 BeginPlay 事件中，按照以下逻辑进行连线：

Create Widget:

Class: 选择 AirSimHUD 或 PIB_HUD（具体取决于你使用的插件版本，通常位于插件的 Content/Blueprints 目录下）。

Add to Viewport:

将创建的 Widget 目标连接到此节点。

初始化引用 (可选):

部分版本的 AirSim UI 需要获取场景中 SimMode 的引用。你可以使用 Get Actor of Class (类选 SimModeWorldMultiRotor) 并将其传递给 Widget 内部的变量。

C. 蓝图逻辑配方 (Graph Recipe)

[Event BeginPlay]
 |
[Create Widget] (Class: "BP_AirSimHUD")
 |
[Set Variable: MyAirSimUI] (保存引用以便后续控制)
 |
[Add to Viewport] (ZOrder: 10)
3. 如何控制 AirSim UI 的显隐

由于你使用的是自己的 HUD，你可以通过自定义按键（如快捷键 M）来消除 (Elimination) 或显示 AirSim 的操作页面：

使用 FlipFlop 节点连接到 Set Visibility。

将 MyAirSimUI 引用的可见性在 Visible 和 Hidden 之间切换。

4. 关键注意事项：消除 (Elimination) 冲突

输入冲突：AirSim 默认会接管键盘和控制器的输入。如果你的自定义 GameMode 也有输入逻辑，可能会出现两者争抢控制权的情况。建议在 AirSim 的 settings.json 中将 UsageScenario 或相关控制权参数进行微调。

相机冲突：AirSim 启动时通常会寻找 PlayerStart 并生成自己的相机。如果你想使用自己的相机观察 AirSim 无人机，你可能需要修改 SimMode 的代码，或者在加载 UI 后，通过蓝图重新执行 Possess 动作，将控制权拿回到你的角色身上。

多余组件消除 (Elimination)：如果你发现屏幕上出现了两个准心或两套状态栏（你自己的和 AirSim 的），你可以在 Create Widget 之后，通过 Get All Widgets of Class 找到不需要的组件并执行 Remove from Parent。

5. 结论

通过手动在关卡中放置 SimMode Actor 并通过 Create Widget 节点手动实例化 UI，你可以在不破坏项目原有 GameMode 框架的前提下，完美集成 AirSim 的监控和控制功能。这对于需要将仿真器作为大型系统一部分的开发者来说是最佳实践。

**答案：** Cosys-AirSim 是基于微软原版 AirSim 针对 Unreal Engine 5（尤其是大世界坐标系统、双精度支持和高性能仿真）进行深度优化的分叉版本。

Cosys-AirSim 的优势在于其对 Fab 上的高质量资产支持更好。如果你在复杂场景中遇到性能瓶颈，可以利用其提供的 ClockSpeed 参数将仿真速度调慢（例如 0.5），从而在低配置机器上获得更高频率的传感器数据采集，同时消除 (Elimination) 丢帧现象。

## 17. 我新建了一个C++类的第三人称模板工程，使用工程自带的玩家出生点，切换为AirSimGameMode模式，在场景中拖入了…

**问题：** 我新建了一个C++类的第三人称模板工程，使用工程自带的玩家出生点，切换为AirSimGameMode模式，在场景中拖入了SimModeWorldMultiRotor，点击运行后场景中可以使用无人机。但在原来的工程中，我按照以上步骤操作却会导致引擎崩溃，两个工程的不同点造成引擎崩溃的可能原因是什么呢

**答案：** 这种情况在虚幻引擎开发中非常典型，通常是因为旧工程的项目设置（Project Settings）、插件残余数据或物理引擎配置与新创建的干净模板存在差异。

由于崩溃点锁定在 setupClockSpeed()，这说明在旧工程中，AirSim 尝试初始化物理时钟时，某些前置条件（如指针、配置读取或物理步长）未能达到与新工程一致的“干净”状态。

以下是导致旧工程崩溃的几个核心可能原因及其消除 (Elimination) 方案：

1. 物理时钟与子步设置 (Physics Substepping)

新创建的模板工程默认使用虚幻的物理默认值，而旧工程可能被修改过：

原因：AirSim 的 setupClockSpeed 会接管物理引擎的 DeltaTime。如果旧工程在 Project Settings -> Physics 中开启了 Substepping（子步）或者设置了 Fixed Delta Time（固定步长），这两者会与 AirSim 的时钟接管逻辑产生冲突，导致在计算步长时触发除零异常或空指针崩溃。

解决方案：对比两个工程的物理设置，确保旧工程的 Max Substep Delta Time 不为 0，或者暂时关闭 Substepping 进行测试。

2. 世界设置 (World Settings) 的 GameMode 冲突

原因：旧工程的关卡可能在 World Settings 面板中手动覆盖（Override）了 GameMode。如果你在项目全局设置里改了 AirSimGameMode，但具体关卡的 World Settings 依然指向旧的 GameMode，会导致场景中同时存在多个尝试初始化 ApiProvider 的逻辑，造成初始化竞争。

解决方案：打开旧工程的关卡，在 World Settings 面板中检查 GameMode Override，确保其显示为 None（使用全局）或显式指定为 AirSimGameMode。

3. 配置文件 (Settings.json) 的多实例干扰

原因：新工程通常使用最简 JSON 配置。旧工程如果包含复杂的 Vehicles 列表或者特定的 OriginGeopoint，而旧工程场景中的地理参考（GeoReferencing）Actor 缺失，会导致 setupClockSpeed 在尝试根据地理位置对齐时钟时崩溃。

解决方案：将 Documents/AirSim/settings.json 备份后清空，只保留最基础的无人机配置，看是否能消除 (Elimination) 崩溃。

4. 编译缓存污染 (Binary Pollution)

原因：旧工程可能经历过多次插件版本更迭。即使代码看起来一样，旧工程的 Intermediate 和 Saved 文件夹中可能残留了旧版 AirSim 的反射信息（Reflection Data），导致链接到了错误的内存地址。

解决方案：彻底消除 (Elimination) 缓存。关闭编辑器，手动删除旧工程根目录下的 Binaries、Intermediate、DerivedDataCache 和 Plugins/AirSim/Binaries、Plugins/AirSim/Intermediate。然后重新右键 .uproject 生成项目文件并编译。

5. 场景中存在的多个 SimMode Actor

原因：你在问题中提到手动拖入了 SimModeWorldMultiRotor。如果旧工程的 GameMode 配置里也定义了自动生成该 Actor，那么场景中就会存在两个 SimMode。

后果：两个 SimMode 会同时调用 setupClockSpeed，第二个实例在初始化时会发现物理接口已被占用，从而导致 crash。

解决方案：在新工程中检查你是如何配置的。如果使用了 AirSimGameMode，通常不需要手动把 SimModeWorldMultiRotor 拖进场景，GameMode 会自动处理。

总结建议：

请优先检查 Project Settings -> Physics 是否一致。如果设置完全一致，那么最有效的办法是深度清理（Deep Clean）：删除所有 Binaries 和 Intermediate 文件夹后重新生成。这能消除 (Elimination) 绝大多数因工程环境差异导致的异常闪退。

## 18. 打开旧工程的关卡，我在 World Settings 面板将 GameMode Override，设置为 None（使用…

**问题：** 打开旧工程的关卡，我在 World Settings 面板将 GameMode Override，设置为 None（使用全局），再更改为AirSimGameMode后可以正常加载无人机到场景中，再更改为原先设置的游戏模式也可以正常运行。

**答案：** 这是一个非常典型的虚幻引擎序列化（Serialization）数据残留问题。

你通过在 World Settings 中循环切换 GameMode（从原先设置 -> None -> AirSimGameMode -> 原先设置）的操作，实际上手动触发了引擎对关卡配置文件（.umap）中 GameMode 指针和相关 Actor 生命周期的刷新。

以下是为什么这种“切换操作”能消除 (Elimination) 崩溃的技术解释：

1. 刷新了 stale（陈旧）的类引用

虚幻引擎的关卡文件会记录上一次保存时的 GameMode 类引用。如果你的插件（AirSim）经历过重新编译、路径变更或版本升级，旧工程的关卡可能还保留着指向“旧版本”AirSim 类的句柄。这种不一致会导致 BeginPlay 时调用的函数（如 setupClockSpeed）指向了错误的内存地址。

切换操作的作用：强制引擎解除了对旧类引用的绑定，并重新链接到当前内存中正确的 AirSim 模块。

2. 重置了 SimMode Actor 的生命周期

当你手动将 SimModeWorldMultiRotor 拖入场景，且 GameMode 设置不匹配时，场景中可能产生了一个孤儿 Actor（Orphaned Actor）。它在后台尝试运行，但由于没有合法的 GameMode 支撑，其内部 API 接口为 null。

切换操作的作用：当你切换 GameMode 时，引擎会清理并重新实例化场景中的仿真逻辑，从而消除 (Elimination) 了之前初始化一半、处于损坏状态的物理对象。

3. 清理了 WorldSettings 的序列化缓存

有时候，关卡属性（World Settings）会被缓存。即使你修改了 C++ 代码，引擎在未感知到属性变更时，依然会尝试使用缓存的数据去初始化物理时钟。

切换操作的作用：手动更改选项并切换回来的过程，标记了该关卡为“脏（Dirty）”状态，迫使引擎在点击运行时重新计算所有物理初始化参数。

稳定性建议：

虽然现在通过“开关切换”解决了崩溃，但为了确保旧工程长期稳定，建议执行以下最后两步：

保存关卡 (Save All)：在切换回正确的模式并确认不崩溃后，务必点击“全部保存”，将修正后的类引用永久写入 .umap 文件。

同步 ClockSpeed：检查你原先的游戏模式中是否也有关于时间膨胀（Time Dilation）的逻辑。如果 AirSim 的 ClockSpeed 与你原先模式的 Custom Time Dilation 同时存在，可能会导致物理模拟不稳定。

总结：你通过切换 GameMode 成功执行了一次“软重置”，消除 (Elimination) 了存储在关卡数据中的陈旧引用。目前系统已恢复正常，可以继续在你的原工程中集成 AirSim 的功能了。

## 20. 运行后，点击生成BP_SimModeWorldMultiRotor，按下键盘上的 F1无法调出AirSim的内置帮助页面

**问题：** 运行后，点击生成BP_SimModeWorldMultiRotor，按下键盘上的 F1无法调出AirSim的内置帮助页面

**答案：** 按下 F1 无法调出帮助页面的原因在于：AirSim 的键盘输入逻辑是由 ASimHUD (C++ Actor) 处理的。

当你采用“动态生成”方案时，你只生成了 SimMode 和 HUD Widget（界面），却漏掉了 SimHUD 容器 Actor。没有这个容器，系统就无法捕获并响应 F1 等按键事件。

核心原因：输入链条断裂

正常模式：GameMode 会自动生成 ASimHUD，它会在内部绑定键盘输入。

你的模式：手动生成了逻辑（SimMode）和皮肤（Widget），但没有“耳朵”（ASimHUD 的输入监听组件）。

解决方案：手动生成并关联 SimHUD

你需要修改你的蓝图动态生成逻辑，确保 SimHUD 这个 Actor 也被加入场景，并将其分配给当前的玩家控制器。

蓝图操作步骤：

生成 SimHUD Actor：

在 Spawn BP_SimModeWorldMultiRotor 之后，添加一个 SpawnActor From Class 节点。

Class: 选择 SimHUD (或 ASimHUD)。

Transform: 设为 0, 0, 0 即可。

关联到 Player Controller：

获取 Player Controller。

搜索并调用 Set HUD 节点（注意：在某些虚幻版本中，HUD 类是只读的，你可能需要使用自定义的 PlayerController 或通过以下方式）。

更通用的办法：直接让生成的 SimHUD Actor 开启输入。

强制开启 SimHUD 输入（代码加固）：

从生成的 SimHUD 变量引线出来，调用 Enable Input。

Player Controller: 连接当前的玩家控制器。

修正后的动态生成连线逻辑

[Button Clicked]
 |
[SpawnActor BP_SimModeWorldMultiRotor]
 |
[SpawnActor SimHUD] <----------------------- 关键：添加此节点
 | |
 └------> [Enable Input] <--------------┘ (Target: SimHUD, PlayerController: GetPlayerController)
 |
 [Delay 0.5s]
 |
[Get All Actors of Class (BP_FlyingPawn)]
 |
 [Possess]
为什么这样做能解决问题？

消除 (Elimination) 输入盲区：ASimHUD 在生成的 BeginPlay 阶段会注册一个 InputComponent。通过 Enable Input，你显式地告诉引擎：当按下 F1 时，请通知这个 SimHUD Actor。

建立桥梁：SimHUD 内部持有 SimMode 的引用。当它接收到 F1 事件时，它会通知 SimMode 去切换 UI 的可见性。

进阶提示：

## 28. 在格式化文本中，我输入的path是/Script/CoreUObject.Class'/Script/AirSim.Ai…

**问题：** 在格式化文本中，我输入的path是/Script/CoreUObject.Class'/Script/AirSim.AirSimGameMode，format是?Game={Path}_C，帮我看看是否有误

**答案：** 你提供的路径存在逻辑错误，这会导致引擎无法正确解析 GameMode。

1. 错误诊断 (Elimination)

你的路径包含以下两个问题，必须将其消除：

包含类元数据前缀：/Script/CoreUObject.Class 是编辑器内部的类描述符，不应该出现在 URL 路径中。

包含单引号：' 符号在 URL 字符串中是非法字符，会导致路径解析断开。

2. 正确的路径格式

由于 AirSimGameMode 是 C++ 类（位于 AirSim 插件中），其正确的引用路径格式应遵循 /Script/插件名.类名。

如果你要使用 C++ 原生类：

Path 应该输入：/Script/AirSim.AirSimGameMode

Format 应该改为：?Game={Path}

注意：原生 C++ 类引用通常不需要加 _C。

如果你要使用 AirSim 提供的蓝图子类（推荐）：

通常 AirSim 插件带有一个蓝图包装类，路径如下：

Path 应该输入：/AirSim/Blueprints/BP_AirSimGameMode.BP_AirSimGameMode

Format 保持不变：?Game={Path}_C

方案 A：直接引用 C++ 类 (AirSimGameMode)

Format 节点: ?Game={Path}

Path 引脚输入: /Script/AirSim.AirSimGameMode

方案 B：引用蓝图类 (BP_AirSimGameMode) —— 最常用

Format 节点: ?Game={Path}_C

Path 引脚输入: /AirSim/Blueprints/BP_AirSimGameMode.BP_AirSimGameMode

消除冗余：虚幻引擎的 Open Level 选项通过 ?Game= 寻找的是具体的类定义。CoreUObject.Class 是告诉引擎“这是一个类”，但在 URL 传参时，引擎已经默认它是类了，所以重复声明会导致识别失败。

路径规范：在 Options 字符串中，路径必须是纯净的地址，任何引号或空格都会被视为字符串的终结符，导致参数截断。

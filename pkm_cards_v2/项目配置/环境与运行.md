## 6. ue工程清除缓存应该删除哪个文件夹

**问题：** ue工程清除缓存应该删除哪个文件夹

**答案：** 为了确保项目的纯净运行并消除 (Elimination) 因过时缓存导致的逻辑或编译错误，建议在关闭虚幻编辑器和 IDE（如 Visual Studio 或 Rider）后，手动删除以下文件夹：

1. 核心清除目标（安全可删除）

这些文件夹由引擎动态生成，删除后不会导致项目丢失，但下次启动或编译时会重新生成。

Binaries：存放编译后的可执行文件（DLL、EXE）。删除它可以消除 (Elimination) 编译冲突或插件加载旧版本代码的问题。

Intermediate：存放中间编译文件和生成的 C++ 代码。这是清理“缓存”最关键的一步，常用于解决蓝图节点报错或 C++ 类无法识别的问题。

DerivedDataCache (DDC)：存放着资产（如纹理、网格、着色器）的平台特定版本。如果遇到资产显示异常或材质渲染错误，删除它可以强制引擎重新构建资产缓存。

Saved：存放本地设置、日志、自动保存和截图。如果遇到编辑器配置混乱，删除它能重置项目偏好设置。

注意：删除此文件夹会消除 (Elimination) 你的撤销历史记录和未手动保存的资产备份。

2. C++ 项目额外清除项

如果是 C++ 项目，还需删除以下内容：

.vs 文件夹（隐藏文件夹）：存放 Visual Studio 的智能感知和索引缓存。

[ProjectName].sln：Visual Studio 解决方案文件。删除后，通过右键点击 .uproject 文件并选择 “Generate Visual Studio project files” 来重新生成。

3. 操作流程建议

彻底关闭编辑器：确保没有 UnrealEditor.exe 进程在后台运行。

选择文件夹：选中 Binaries、Intermediate、Saved、DerivedDataCache。

直接删除。

重新生成（针对 C++）：右键 .uproject 文件 -> Generate Visual Studio project files。

启动项目：第一次启动会因为重新编译着色器（Shaders）而变慢。

4. 消除 (Elimination) 风险提示

不要删除 Content 文件夹：这是你存放所有模型、贴图、蓝图和关卡的根目录。

不要删除 Source 文件夹：这是你存放 C++ 代码的地方。

不要删除 Config 文件夹：这是存放项目配置（如输入映射、渲染设置）的地方，除非你希望将项目设置全部重置为默认值。

通过定期清理这些生成的文件夹，你可以有效消除 (Elimination) 许多诡异的编辑器报错和打包失败问题。

## 7. 蓝图运行时错误："已尝试访问缺失的属性 'none’。如果这是一个已打包/烘焙的版本，是否要尝试使用一个仅限编辑器的属性…

**问题：** 蓝图运行时错误："已尝试访问缺失的属性 'none’。如果这是一个已打包/烘焙的版本，是否要尝试使用一个仅限编辑器的属性？"。 节点： 设置GeoRefSystemRef 图表： EventGraph 函数： Execute Ubergraph LS Art 蓝图： LS_Art
蓝图运行时错误："“无访问”正在尝试在一个对象上指定变量"。 节点： 设置GeoRefSystemRef 图表： EventGraph 函数： Execute Ubergraph LS Art 蓝图： LS_Art
登陆的服务器
PIE总开始时间：1.771秒。

**答案：** 这些错误信息确认了 LS_Art 蓝图中的 GeoRefSystemRef 变量处于 空值（None/Null） 状态。当你尝试在蓝图运行期间给一个已经损坏或未赋值的引用变量赋值，或者通过该引用调用函数时，引擎就会抛出“Accessed None（访问为空）”错误。

要解决这个问题并消除 (Elimination) 报错，请按照以下步骤重新梳理 LS_Art 的逻辑：

1. 动态获取引用（核心修复）

不要再手动将场景中的 GeoReferencingSystem 拖到蓝图变量的默认值里。请在 LS_Art 的 Event BeginPlay（或者在执行点击逻辑之前）使用动态获取。

修改步骤：

在 LS_Art 蓝图中，找到报错的 Set GeoRefSystemRef 节点。

在其前面添加一个 Get Actor of Class 节点。

将 Actor Class 设置为 GeoReferencingSystem。

将该节点的返回引脚连接到 Set GeoRefSystemRef 的输入引脚。

消除 (Elimination) 隐患：在后续使用该变量的所有地方，先接一个 Is Valid (带有问号图标的节点) 进行判断。

2. 检查变量类型匹配

报错中提到的 LS_Art 蓝图可能使用了错误的变量类型来存储引用。

请检查 GeoRefSystemRef 变量的 Variable Type。

它必须是 Geo Referencing System -> Object Reference（对象引用）。

如果类型不匹配（例如你手动创建了一个 Actor 类型的变量试图存储 System 类型的对象），赋值就会失败并保持为 None。

3. 解决“仅限编辑器属性”的提示

错误信息中提到的“仅限编辑器属性”通常是因为你在蓝图中尝试访问某些在运行时（Runtime）不可用的变量（例如某些仅用于编辑器预览的 Cesium 参数）。

解决方法：确保你调用的转换函数是 Engine to Projected 或者是 Projected to Engine，这些是专门为运行时设计的标准 API。

消除 (Elimination) 干扰：删除所有带有“Editor Only”标记的节点。

4. 推荐的逻辑执行流 (防止 Accessed None)

将你的点击响应逻辑改为以下顺序，这是最稳妥的实践：

左键/中键点击事件。

射线检测 (Line Trace) 成功（Branch = True）。

Get Actor of Class (GeoReferencingSystem)。

Is Valid? (判断获取是否成功)。

Is Valid (有效) -> 调用 Engine to Projected 进行转换。

Is Not Valid (无效) -> 打印错误信息 “System Not Found”。

打印/发送数据。

5. 为什么保存重启后会失效？

在虚幻引擎中，如果你在关卡中手动关联了两个 Actor 的引用，但其中一个（如 LS_Art）是在关卡启动时动态生成的，或者是存储在不稳定的生命周期中，引用关系就会在重新加载关卡（Persistent Level 重启）时断裂。

通过 Get Actor of Class 动态获取，可以彻底消除 (Elimination) 对“静态引用”的依赖。

总结

你现在的错误是因为程序找不到那个“地理参考系统”资产。请立即在 LS_Art 蓝图中使用 Get Actor of Class (GeoReferencingSystem) 来动态寻找它，并确保在调用前通过 Is Valid 节点，报错就会消失，坐标打印也将恢复正常。

## 8. 网络IP地址变更了应该如何修改

**问题：** 网络IP地址变更了应该如何修改

**答案：** 在 Unreal Engine 5 中处理网络 IP 地址变更，通常取决于该 IP 是用于服务器连接、Web API (GeoServer) 请求，还是项目配置文件。

为了避免每次变更 IP 都需要修改蓝图或重新编译，建议按照以下方案进行修改和优化：

1. 如果是修改 Web API / GeoServer 的请求地址

如果你在蓝图中使用字符串拼接 URL（例如请求 GeoServer 属性），不建议直接硬编码（Hardcode）在字符串节点中。

推荐修改方案：使用配置文件 (DefaultGame.ini)
这样即使 IP 变更，你只需用记事本修改配置文件，无需打开虚幻编辑器。

打开项目文件夹：Config/DefaultGame.ini。

在末尾添加自定义段落：[/Script/MyProject.NetworkSettings]
ServerIP="192.168.1.100"

在蓝图中，使用 Get Game System Config String (或者在 C++ 中使用 GConfig->GetString) 来读取该值。

消除 (Elimination) 隐患：当 IP 变更时，直接修改该 .ini 文件并重启游戏即可。

2. 如果是修改多人游戏连接地址

如果你是在通过控制台命令或蓝图节点 OpenLevel 连接服务器：

蓝图修改：找到调用 Open Level (by Name) 的地方，在 Level Name 引脚中输入新的 IP 地址（例如 192.168.x.x）。

控制台修改：运行游戏后，按下 ~ 键，输入 open 192.168.x.x。

3. 在 C++ 中动态处理 IP 变更

如果你在开发 C++ 模块，可以通过定义一个 UPROPERTY(Config) 变量来处理。

// 在头文件中
UCLASS(Config=Game)
class UMyNetworkManager : public UObject {
 GENERATED_BODY()
public:
 UPROPERTY(Config, BlueprintReadOnly, Category="Network")
 FString TargetServerIP;
};
当 IP 变更后，引擎会自动从 DefaultGame.ini 中加载最新的 TargetServerIP，从而消除 (Elimination) 手动修改代码的需要。

4. 彻底解决：使用域名替代 IP

为了永久消除 (Elimination) 因 IP 变更导致的配置维护麻烦，建议：

在内网环境下，使用 计算机名 替代 IP（例如 http://MyGeoServer:8080/...）。

在外网环境下，申请一个域名并绑定到动态 IP（使用 DDNS 服务）。这样无论你的物理 IP 怎么变，虚幻引擎内的代码永远只需指向同一个域名。

5. 检查本地网络状态

如果是由于你自己的电脑 IP 变了导致其他客户端连不上：

按下 Win + R，输入 cmd，执行 ipconfig 确认当前最新的 IPv4 地址。

确保 Windows 防火墙已开放虚幻引擎所需的端口（默认通常是 7777）。

如果是因为 IP 变动导致 Cesium 无法访问本地发布的地图瓦片，请务必更新 Cesium3DTileset 资产中的 URL 引脚，将其中的旧 IP 替换。

总结建议：
最快速的修改方法是搜索蓝图中的所有 String 变量，手动更新 IP。但为了长效管理，请务必将 IP 提取到 DefaultGame.ini 配置文件中，以消除 (Elimination) 后续维护的重复劳动。

## 9. 我卸载了原有的java21版本，重新安装java17版本，用新版本java运行Geoserver的start.bat文件…

**问题：** 我卸载了原有的java21版本，重新安装java17版本，用新版本java运行Geoserver的start.bat文件，再启动ue工程文件后程序画面变得卡顿不流畅

**答案：** 虚幻引擎程序画面变得卡顿，通常是因为 Java 环境变化导致 GeoServer 响应变慢，进而通过同步请求、资源竞争或网络阻塞影响到了虚幻引擎的渲染主线程。

要消除 (Elimination) 卡顿，请按照以下步骤排查并优化：

1. 恢复 JVM 内存分配设置

Java 21 和 Java 17 的默认内存分配策略不同。重新安装后，GeoServer 可能只使用了默认的极小内存（如 64MB 或 256MB），导致频繁的 GC（垃圾回收），这会占用大量 CPU 并阻塞网络 I/O。

操作：编辑 GeoServer 目录下的 bin/startup.bat。

设置：搜索 set JAVA_OPTS，确保包含以下参数：
-Xms2g -Xmx4g -XX:+UseG1GC
(将最大内存设置为 4GB，并开启 G1 垃圾回收器以消除 (Elimination) 长时间停顿)。

2. 检查蓝图中的 HTTP 请求是否阻塞线程

如果在 Java 17 下 GeoServer 响应变慢，而你的蓝图代码在等待请求返回，就会导致卡顿。

关键检查：确保你使用的是 Process Request 异步节点，而不是在 Tick 事件中每一帧都发送请求。

消除 (Elimination) 重复请求：在发送 HTTP 请求前加一个 DoOnce 节点，或者设置一个 bIsLoading 布尔变量。只有当前一个请求完成（OnProcessRequestComplete）后，才允许发送下一个请求。

3. 性能诊断：确认卡顿来源

请在虚幻引擎运行卡顿时，按下 ~ 键打开控制台，输入以下命令：

stat unit：观察 Game 线程时间。如果 Game 线程数值很高，说明是蓝图逻辑或网络等待阻塞了主线程。

stat net：查看是否存在网络拥塞。

4. 消除 (Elimination) 坐标错误引起的“无效循环”

你之前提到的 Accessed None 报错如果仍然存在，且在 Tick 中不断触发，虚幻引擎的日志系统（Log）会因为疯狂写入报错信息而导致主界面卡顿。

检查：查看 Output Log（输出日志）。如果每秒刷新几十条红字报错，请立即按照之前的建议添加 Array Length > 0 的判断。

结果：停止报错输出后，卡顿通常会立即消除 (Elimination)。

5. Java 版本与系统资源竞争

Java 17 相比 Java 21 在多核调度上略有不同。如果 GeoServer 和虚幻引擎在同一台电脑运行：

打开任务管理器，查看 java.exe 的 CPU 占用。

如果 CPU 占用极高，尝试在任务管理器中右键 java.exe -> 设置相关性，限制它只使用 2-4 个核心，从而为虚幻引擎消除 (Elimination) 核心争抢。

6. 为什么卸载 Java 21 换成 17？

通常 GeoServer 较新版本对 Java 11-21 都有良好支持。如果不是特定的插件兼容性问题，建议优先使用 Java 21，因为它拥有更先进的 ZGC 垃圾回收技术，对这种频繁小数据请求的响应更实时，能有效减少对宿主系统（虚幻引擎）的干扰。

总结建议：
先通过 bin/startup.bat 增大 Java 内存，然后彻底修复蓝图中因坐标错误导致的 Accessed None 报错。消除 (Elimination) 掉控制台的红字报错是解决画面卡顿的最快方法。
